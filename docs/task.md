# CyberSaathi AI — Sequential Build Plan (4 Days)

> **Purpose:** This is the execution checklist for Antigravity. Follow tasks in order, keep the application functional, and verify each task before moving on. The four-day limit is strict. Prioritize a complete, tested end-to-end product over optional features.

## Non-negotiable project rules
1. Inspect the existing repository before creating, replacing, or deleting files.
2. Treat existing source code and actual tests as the authority for implementation status. Never assume a feature exists because it appears in a concept note.
3. Do not invent dataset sources, dataset sizes, model metrics, integrations, user counts, deployment status, or test results.
4. Never automatically open, fetch, crawl, or navigate to a user-submitted URL. URL analysis must use string parsing and local feature extraction only.
5. Do not call content “safe.” Use cautious categories such as `High Risk`, `Suspicious`, and `No Obvious Warning Signs`.
6. Do not add a paid LLM API dependency. The core product must work without an API key.
7. Avoid collecting or persisting submitted messages/URLs. Do not log raw submissions.
8. `design.md` will be supplied separately. Until then, build accessible, polished, responsive UI without inventing elaborate visual requirements. Once supplied, follow it unless it conflicts with safety, feasibility, or this PRD.
9. Keep each task small enough to verify. If time runs short, finish the core flow and tests before optional polish.
10. Make meaningful Git commits using the statements in `prompts.md`. Never claim a commit was made unless it was actually made.

## Four-day delivery strategy
- **Day 1:** Repository inspection, project setup, dataset/model feasibility, reproducible baseline.
- **Day 2:** Complete backend APIs and tests; integrate actual model artifacts.
- **Day 3:** Functional frontend, API integration, English/Hinglish explanations, learning content.
- **Day 4:** End-to-end testing, security/privacy review, deployment if feasible, documentation and evidence.

## Task sequence

### T-00 — Inspect repository and establish baseline
**Priority:** Critical | **Day:** 1 | **Prompt:** P-00
- Inspect repository tree, Git status/history, installed dependencies, existing code, documentation, and available environment.
- Identify what is implemented, partial, missing, or unverified.
- Do not overwrite working code without understanding it.
- Record findings and propose a minimal implementation plan consistent with the four-day deadline.
**Acceptance:** A concise audit exists; no destructive changes were made; actual project structure is understood.

### T-01 — Lock architecture, contracts, and project skeleton
**Priority:** Critical | **Day:** 1 | **Prompt:** P-01
- Establish a clear frontend/backend/model directory structure.
- Define API contracts for health, URL analysis, message analysis, and learning/quiz content if needed.
- Establish configuration, environment-variable conventions, CORS policy, input-size limits, and test commands.
- Keep frontend and backend independently runnable.
**Acceptance:** Project starts in a documented minimal state; API request/response contracts are recorded; no secrets are committed.

### T-02 — Dataset verification and reproducible ML baselines
**Priority:** Critical | **Day:** 1–2 | **Prompt:** P-02
- Find accessible public datasets suitable for URL classification and, if feasible, message classification.
- Verify provenance, access, license/terms, labels, data format, class balance, and limitations before use.
- If downloading is blocked or licensing is unclear, do not fabricate a dataset. Implement the URL baseline with a documented, legitimate dataset already available; otherwise stop and report the blocker.
- Build deterministic preprocessing, leakage-aware train/validation/test split, baseline training, evaluation, and saved artifacts.
- Prioritize URL classifier first. Message classifier is a separate model and must not be presented as trained if it is not.
- Evaluate precision, recall, F1-score, confusion matrix, and false negatives/positives. Save actual outputs.
**Acceptance:** Training is reproducible; artifacts can be loaded; metrics are generated by actual runs; dataset provenance and limitations are documented.

### T-03 — Backend analysis services and API tests
**Priority:** Critical | **Day:** 2 | **Prompt:** P-03
- Implement FastAPI endpoints: `/health`, `/api/analyze/url`, and `/api/analyze/message`.
- Validate types, empty input, maximum length, URL format, and malformed requests.
- Load real model artifacts at startup when available.
- Keep ML predictions separate from rule-based indicators. Include method/source labels in the response.
- If a model cannot be trained with valid data in the four-day window, use a clearly disclosed deterministic rules-based fallback and label it as such. Do not call this ML.
- Return stable structured JSON, actionable advice, cautious risk labels, and language selection.
- Add tests for normal, suspicious, benign-looking, malformed, oversized, and empty inputs.
**Acceptance:** Backend starts; endpoints respond correctly; tests pass; submitted URLs are never requested/opened; no raw input is logged.

### T-04 — Frontend application and end-to-end integration
**Priority:** Critical | **Day:** 3 | **Prompt:** P-04
- Implement URL/message mode selection, input forms, validation, loading/error/success states, and clear result sections.
- Connect to real backend endpoints. Do not use mock results in the final build.
- Show risk category, model/rule source, warning indicators, explanation, practical next steps, and limitations.
- Include English/Hinglish explanation toggle without claiming the model itself is validated on Hinglish unless evidence supports that.
- Make the application responsive and keyboard accessible.
**Acceptance:** Both analysis flows work from the browser through the API; API failures are visible and recoverable; no fake output is shown.

### T-05 — Cybersecurity learning section and quizzes
**Priority:** High | **Day:** 3 | **Prompt:** P-05
- Add focused educational content: phishing basics, suspicious links, internship/job scams, scholarship/payment scams, password/OTP safety, independent verification, and response after a suspected compromise.
- Add a small quiz with answer feedback and explanations.
- Keep content locally bundled and usable without paid APIs.
**Acceptance:** Lessons and quizzes work; answers and explanations are internally consistent; no external API is required.

### T-06 — Privacy, security, quality, and accessibility hardening
**Priority:** Critical | **Day:** 4 | **Prompt:** P-06
- Review input validation, exception handling, CORS, secrets, logs, dependencies, and model-loading failure paths.
- Ensure no submitted URL is opened or fetched, no raw input is stored/logged by default, and secrets are not in frontend code.
- Add privacy notice, limitations/disclaimer, and safe next-step guidance.
- Run backend tests, frontend build/lint/tests if configured, and end-to-end smoke checks.
- Fix real failures; do not suppress tests or weaken assertions to obtain a green result.
**Acceptance:** Actual commands/results are recorded; critical issues are fixed or clearly listed as blockers; app handles expected failure states.

### T-07 — Deployment and reproducible documentation
**Priority:** High | **Day:** 4 | **Prompt:** P-07
- Deploy only after local end-to-end verification. Use the simplest suitable free-tier hosting supported by the app.
- Keep frontend and backend configuration explicit. Do not expose secrets.
- Configure the deployed frontend origin in backend CORS.
- If deployment is blocked by time, platform limits, or model artifact size, finish local reproducibility and capture screenshots instead of pretending deployment succeeded.
- Update README, setup instructions, architecture, dataset/model documentation, API docs, test evidence, and known limitations.
**Acceptance:** Either a verified live URL works end-to-end, or the local setup is reproducible and deployment blocker is documented honestly.

### T-08 — Final evidence and handoff
**Priority:** Critical | **Day:** 4 | **Prompt:** P-08
- Run the documented clean-start procedure.
- Test URL analysis, message analysis, language toggle, learning/quiz, invalid input, backend unavailable, and mobile/responsive behavior.
- Capture real screenshots and save them in the repository.
- Check Git status and remove accidental secrets, datasets/artifacts that should not be committed, caches, and local environment files.
- Prepare a short list of implemented features, measured metrics, commands tested, known limitations, and deployment status.
**Acceptance:** Another person can run or access the app using the README and see the complete workflow; claims match evidence.

## De-scope order if time is running out
1. Preserve: real end-to-end analysis flow, input safety, accurate labels, tests, README.
2. Preserve if feasible: actual URL model and evaluation.
3. Keep message analysis rule-based with explicit disclosure if a legitimate text dataset/model is not feasible.
4. Keep a small learning section and quiz.
5. Defer: accounts, database, history, admin panel, live threat intelligence, browser extension, crawling, analytics, fancy animations, and LLM integration.

## Definition of done
The project is complete only when the app starts reproducibly, both analysis workflows behave as documented, output sources are transparent, no submitted URL is opened, privacy safeguards are in place, actual tests are run, and documentation matches reality.
